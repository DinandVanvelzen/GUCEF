# CLAUDE.md - AI Assistant Notes for GUCEF Repository

This file contains important notes and reminders for AI assistants working on this codebase.

## Build System Notes

### Project Files Are Generated: Use ProjectGenerator

The build files of every module are generated by **ProjectGenerator** (`tools/ProjectGenerator`, library `tools/ProjectGen`)
from a few input files. To add, remove or rename source files, add a module, or change dependencies, defines, the C++
standard, include directories or platforms: change the inputs and regenerate. Do **not** edit generated files by hand.

1. **Inputs (edit these)**
   - `ModuleInfo.xml` in the root directory of a module: module name, type (`Executable`, `SharedLibrary`, `StaticLibrary`,
     `HeaderIncludeLocation`, ...), `Platform`, `Tags`, `<Dependencies>`, `<Linker>`, `<Preprocessor>` defines,
     `<Compiler MinCppStandard="..">` with per-compiler `CompilerFlags`, `<Includes Source="Self|Dependency|ExcludedFromSearchPaths">`,
     `<RuntimeDependencies>`. The entry with the module name is the template; entries with only a `Platform` add to or
     override it for that platform. The full format is in `tools/ProjectGenerator/README.md`.
   - `ProjectGenInstructions.xml` in any directory of a module: `<EXCLUDES PLATFORM="..">` and `<INCLUDES PLATFORM="..">`
     with `<ITEM NAME=".." TYPE="FILE|DIR" />` to leave files or directories out (per platform) or to add files from
     elsewhere (`../OtherModule/src/file.cpp`).
   - `ProjectGenExcludeList.txt`: directories the generator does not scan.
   - The source files themselves: the generator finds the `.h`, `.c` and `.cpp` files by scanning the module directory, so
     a new, removed or renamed file only needs a regeneration.

2. **Outputs (never edit by hand)**
   - Per module: `CMakeLists.txt`, `premake4.lua`, `premake5.lua`, `Android.mk`.
   - Aggregates: `projects/CMake/modules/*`, `projects/CMake/targets/*` (`*_ModuleDirs.cmake`), `projects/premake5/targets/*`,
     `projects/Android/targets/*`, `projects/CI/*`, `.github/workflows/*`, `Project.xml` and `premake4.lua` in the root.
   - Visual Studio project files come from CMake (see item 4).

3. **How to regenerate (Linux)**
   1. Build the generator, once and again after `tools/ProjectGen` or `tools/ProjectGenerator` changed (also after a pull
      that changed them):
      ```bash
      cmake -G Ninja -S projects/CMake/targets/GUCEF_exe_ProjectGenerator -B common/bin/CBNINJA_ProjectGenerator \
            -DCMAKE_BUILD_TYPE=debug -DCMAKE_POLICY_VERSION_MINIMUM=3.5
      ninja -C common/bin/CBNINJA_ProjectGenerator
      ```
   2. Run it from the repository root with `GUCEF_HOME` set to the repository root. The ini finds the root and the
      output directories through `$ENVVAR:GUCEF_HOME$`; without it the outputs get wrong paths (`/projects/...`). Use the
      debug ini with the project info cache switched off, so the result reflects the tree as it is:
      ```bash
      sed 's/"useProjectInfoCache"="true"/"useProjectInfoCache"="false"/' projects/ProjectGenerator_d.ini > /tmp/pg_nocache_d.ini
      GUCEF_HOME=$PWD GUCEF_CONSOLE_LOGGER=none LD_LIBRARY_PATH=common/bin/CBNINJA_ProjectGenerator/lib \
          common/bin/CBNINJA_ProjectGenerator/bin/ProjectGenerator "*ConfigPath=/tmp/pg_nocache_d.ini*BootstrapConfigPath=/tmp/pg_nocache_d.ini*"
      ```
      It takes a few minutes and writes `ProjectGenerator_Log.txt` (git ignored) in the root. `projects/GenerateProjectFiles.sh`
      only finds a generator binary (its invocation is commented out): do not rely on it.
   3. Review `git status` and `git diff`. The generator rewrites the files of every module it scans, so the result can
      also hold changes of modules you did not touch (drift from earlier hand edits or other work). Keep the files of
      the modules you changed and the aggregate lists insofar they reflect your change; restore the rest with
      `git checkout -- <file>` unless a full regeneration is the intent. Check the library type of modules with
      per-platform types (for example the Android `StaticLibrary` entries of `OgreRenderSystem_GLES2` and
      `OgreRenderSystem_Vulkan`): the generator has been seen to drop or add `STATIC` in `add_library` between runs.
   4. Build the targets that changed: `cmake -G Ninja -S projects/CMake/targets/GUCEF_exe_<target> -B common/bin/CBNINJA_<target>
      -DCMAKE_BUILD_TYPE=debug -DBUILD_SHARED_LIBS=ON -DCMAKE_POLICY_VERSION_MINIMUM=3.5` and `ninja -C common/bin/CBNINJA_<target>`.

   **With other uncommitted work in the tree** (other sessions, other people), regenerate in a scratch worktree and copy
   back only the generated files you need, so nothing of that work is rewritten:
   ```bash
   G=$PWD; W=/tmp/pgregen                                       # G: the main tree, with the built generator
   git worktree add -q --detach $W HEAD
   git diff --binary HEAD | git -C $W apply                     # the uncommitted changes
   git ls-files --others --exclude-standard -z | xargs -0 -I{} cp --parents {} $W/   # the new files
   git -C $W add -A                                             # git status in $W now shows only what the generator writes
   (cd $W && GUCEF_HOME=$W GUCEF_CONSOLE_LOGGER=none LD_LIBRARY_PATH=$G/common/bin/CBNINJA_ProjectGenerator/lib \
       $G/common/bin/CBNINJA_ProjectGenerator/bin/ProjectGenerator "*ConfigPath=/tmp/pg_nocache_d.ini*BootstrapConfigPath=/tmp/pg_nocache_d.ini*")
   git -C $W status --porcelain | grep -v '^[AMD]  '            # what is left is generator output; copy the wanted files back
   git worktree remove --force $W
   ```
   (Run the commands from the repository root, after making `/tmp/pg_nocache_d.ini` as in step 2.)

   **On Windows**: build `GUCEF_exe_ProjectGenerator` with CMake the same way, then run `ProjectGenerator.exe` from the
   repository root with `set GUCEF_HOME=%CD%` and the same `*ConfigPath=...*BootstrapConfigPath=...*` argument.

   **Repositories built on GUCEF** (GalaxyUnlimited, ...) run the generator through their own script
   (`tools/generate-build-files.sh`) over their tree plus the GUCEF directories listed in its `GUCEF_ROOTS`. That run
   rewrites the generated files of those GUCEF modules with that repository's ini: back up the GUCEF generated files
   before it and restore any it changed afterwards.

   A hand edit of a generated file list is only a stop gap when the generator cannot be run; regenerate before committing.

4. **Do NOT manually edit Visual Studio project files**
   - Visual Studio project files (`.vcxproj`, `.vcxproj.filters`, `.sln`) are **generated from CMake**
   - Do not manually edit these files to add/remove source files
   - Instead, change the ProjectGenerator inputs, regenerate (item 3) and run a build
   - The build process will regenerate the Visual Studio project files
   - After regeneration, Visual Studio will prompt to reload the modified project files

5. **Triggering builds from within Visual Studio**
   - Use the `build_solution` or `build_project` MCP tools to trigger a build from within Visual Studio
   - These tools are provided by the **VS MCP Server** extension (see Visual Studio Setup below)
   - Always trigger a build after regenerating the CMake files to ensure changes are picked up

### Visual Studio 2026 Pro Setup

**CRITICAL: Do NOT assume Visual Studio is not running.** The user works inside Visual Studio 2026 Pro and launches Claude Code from within it via the Claude Code Extension. If MCP tools are unavailable or a port check fails, this does NOT mean VS is not running — it may mean the VS MCP Server extension is not yet active. Before asking or stating that VS is not running, first verify by checking running processes (`tasklist | findstr devenv`). The solution is always open when this session is active.

**CRITICAL: VS MCP Server requires manual "Start server" click.** The VS MCP Server extension does NOT start automatically when Visual Studio opens. The user must manually click **"Start server"** in the VS MCP Server extension panel each time Visual Studio is launched. If `build_project` / `build_solution` and other VS MCP tools are unavailable, remind the user: **"Please click 'Start server' in the VS MCP Server extension panel inside Visual Studio."**

If you detect you are running inside Visual Studio 2026 (e.g., told so by the user, or the session context indicates it), check whether the following MCP tools are available: `build_solution`, `document_open`, `solution_info`, etc.

If these tools are **not available**, prompt the user to install the required extensions:

1. **Claude Code Extension** (chat UI inside VS):
   - https://marketplace.visualstudio.com/items?itemName=dliedke.ClaudeCodeExtension

2. **VS MCP Server** (exposes VS GUI control as MCP tools):
   - https://marketplace.visualstudio.com/items?itemName=CodingWithCalvin.VS-MCPServer
   - After installing, register it with Claude Code by running (from a standalone terminal, NOT inside a Claude session):
     ```
     claude mcp add vs-mcp-server --transport sse http://localhost:5050/sse --scope user
     ```
   - The `--scope user` flag is required to make it available across all projects (valid scopes: local, user, project, dynamic, enterprise, claudeai, managed)
   - Do NOT run this from inside a Claude session - it won't persist correctly
   - Then restart the Claude Code session so the new tools are loaded

**Available MCP tools once configured:**
- `solution_info` / `solution_open` / `solution_close` - Solution management
- `project_list` / `project_info` - Project metadata
- `document_list` / `document_active` / `document_open` / `document_read` / `document_write` - File/editor control
- `selection_get` / `selection_set` / `editor_insert` / `editor_replace` / `editor_goto_line` / `editor_find` - Editor operations
- `build_solution` / `build_project` / `clean_solution` / `build_cancel` / `build_status` - Build control

6. **Platform-specific implementations (IMPORTANT)**
   - Source and header files often have platform-specific implementations in subdirectories
   - When changing an interface, ALWAYS check platform subdirectories for implementations
   - Common platform subdirectories under `src/` and `include/`:
     - `mswin/` - Windows-specific code
     - `linux/` - Linux-specific code
     - `android/` - Android-specific code
     - `apple/` or `macos/` - macOS-specific code
   - Example: `platform/gucefCORE/src/mswin/CMSWinConsoleLogger.cpp`
   - Example: `platform/gucefCORE/include/android/gucefCORE_CAndroidSystemLogger.h`
   - These files may not be part of the current project build (e.g., Android files on Windows)
   - But they MUST be updated to maintain cross-platform compatibility

7. **Check tools/ folder when changing interfaces**
   - The `tools/` folder contains applications and libraries that may implement or use interfaces defined in `platform/`
   - When changing an interface in gucefCORE (e.g., CILogger), check for implementations in:
     - `tools/GucefLogServiceLib/` - Log service library with CILogSvcServerLogger interface
     - `tools/GucefLogServiceApp/` - Log service application
     - `tools/GucefLogServiceClientPlugin/` - Log service client plugin
     - Other tools that may depend on the changed interface
   - These may not be in the current Visual Studio solution but need to be updated for consistency

## Code Style Notes

### File Naming Conventions

- Header files: `gucefCORE_CClassName.h` (module prefix + class name)
- Source files: `gucefCORE_CClassName.cpp` (matching header name)
- Test files: `TestClassName.h` / `TestClassName.cpp`

### Include Guard Pattern

```cpp
#ifndef GUCEF_CORE_CCLASSNAME_H
#define GUCEF_CORE_CCLASSNAME_H
// ... content ...
#endif /* GUCEF_CORE_CCLASSNAME_H ? */
```

### Include Pattern

```cpp
#ifndef GUCEF_CORE_SOMEFILE_H
#include "gucefCORE_SomeFile.h"
#define GUCEF_CORE_SOMEFILE_H
#endif /* GUCEF_CORE_SOMEFILE_H ? */
```

### Namespace Pattern

```cpp
namespace GUCEF {
namespace CORE {
// ... content ...
}; /* namespace CORE */
}; /* namespace GUCEF */
```

### Tracing

- Add `{GUCEF_TRACE;` at the start of function bodies for tracing support

### Logging

- **Always use GUCEF logging macros**, not `std::cout` or other direct output
- The GUCEF logging system directs output to the appropriate logging outputs based on platform and application preferences
- Common logging macros (from `gucefCORE_Logging.h` / `gucefCORE_LoggingMacros.h`):
  - `GUCEF_LOG( logLevel, message )` - General logging
  - `GUCEF_DEBUG_LOG( logLevel, message )` - Debug-only logging
  - `GUCEF_ERROR_LOG( logLevel, message )` - Error logging
  - `GUCEF_WARNING_LOG( logLevel, message )` - Warning logging
- Log levels: `LOGLEVEL_CRITICAL`, `LOGLEVEL_NORMAL`, `LOGLEVEL_BELOW_NORMAL`, `LOGLEVEL_EVERYTHING`

### C++ Feature Compatibility Macros

The codebase supports older C++ compilers. Use these macros from `gucef_cpp.h`:

- **Move semantics**: Use `#ifdef GUCEF_MOVE_SEMANTICS_SUPPORTED` to guard move constructors and move assignment operators
  - Use `GUCEF_MOVE( m )` instead of `std::move( m )` - it falls back gracefully on older compilers
  - Some older code may use `GUCEF_RVALUE_REFERENCES_SUPPORTED` (equivalent, but prefer `GUCEF_MOVE_SEMANTICS_SUPPORTED` for new code)
- **noexcept**: Use `GUCEF_NOEXCEPT` instead of `noexcept`
- **override**: Use `GUCEF_VIRTUAL_OVERRIDE` instead of `override`

Example:
```cpp
class MyClass
{
    #ifdef GUCEF_MOVE_SEMANTICS_SUPPORTED
    MyClass( MyClass&& src ) GUCEF_NOEXCEPT;
    MyClass& operator=( MyClass&& src ) GUCEF_NOEXCEPT;
    #endif
};

// In implementation:
#ifdef GUCEF_MOVE_SEMANTICS_SUPPORTED
MyClass::MyClass( MyClass&& src ) GUCEF_NOEXCEPT
    : m_member( GUCEF_MOVE( src.m_member ) )
{GUCEF_TRACE;
}
#endif
```

## Workflow Notes

### When Facing Complex Changes or Multiple Errors

- **Ask for feedback/input** when changes get complex or there are multiple compile errors to fix
- Do NOT attempt to revert changes or make large-scale fixes without checking with the user first
- This avoids undoing wanted work and wasting tokens on trial-and-error approaches
- If unsure about the intended direction, stop and ask rather than guessing

### File Replacement Safety Protocol

**NEVER delete files directly when doing whole-file replacement.** Follow this protocol:
1. Write new content to a temporary file first (e.g., `filename.h.new`)
2. Check if the original file has uncommitted changes (`git status` or `git diff`)
3. If uncommitted changes exist: **ASK USER PERMISSION** before proceeding
4. Only after user approval: rename original to `.old`, rename `.new` to original
5. User can then review and delete the `.old` file

This prevents data loss from uncommitted work.

### Test Code Guidelines

- **NEVER remove try-catch blocks from test code** - exception handling is critical
- Tests can fail and throw exceptions - that's the whole point of having tests
- One test's uncaught exception should NOT crash and prevent other tests from running
- When converting tests to use the test framework:
  - Keep all existing try-catch blocks
  - The `GUCEF_TESTFW_TESTCASE` / `GUCEF_TESTFW_TESTCASE_END` macros work alongside try-catch, not as replacements
  - Wrap the test body in try-catch INSIDE the test case macros
- Example pattern:
  ```cpp
  GUCEF_TESTFW_TESTCASE( "Test name" )
      try
      {
          // test code with ASSERT_TRUE etc.
      }
      catch( ... )
      {
          ERRORHERE;
      }
  GUCEF_TESTFW_TESTCASE_END
  ```

### Investigating Claude Code / MCP Issues

- When troubleshooting Claude Code configuration or MCP server issues, check `~/.claude.json` (home directory) — this file contains the actual runtime state including registered MCP servers, per-project settings, and tool allowlists
- Do NOT assume the configuration is missing just because it's not in `~/.claude/settings.json` — they serve different purposes
- Read the file contents before drawing conclusions; do not guess at what might be configured

### Progress Tracking for Multi-File Tasks

- **When doing structured tasks across multiple files (like converting all tests), use the planning tools**
- Call `plan` at the start to create a tracked plan with steps for each file
- Use `update_plan_progress` to mark files as completed
- This prevents re-reading already-processed files and wasting tokens
- Keep mental notes of what's already been accomplished in the current session
- If interrupted, check the plan state before resuming work
